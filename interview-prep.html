System32 · Interview prep

A fake Windows 11 desktop in the browser that is "corrupted"; you repair it by beating mini-games, then find bonus games in the Recycle Bin, one of which is a full voxel survival game. Vanilla HTML/CSS/JS, no build step, no dependencies except three.js for the 3D games.

The 60-second pitch

System32 is a browser "operating system" built with no framework and no build step. A shell (windows, taskbar, Start menu, Explorer, Notepad, a browser called Edgy, Settings, Recycle Bin) hosts games in sandboxed iframes. Each game talks to the shell only through postMessage, so the shell owns all progress and a game cannot cheat its way into the save. Three core games repair the system; after the ending two bonus games unlock: SpaceSaga (a 3D endless runner) and Strata, a Minecraft-style voxel game with survival, mobs, a boss and an ending, written from scratch (chunked world, worker-based meshing, smooth light, A* pathfinding, flowing water, multiple worlds). I directed the design and decisions and used Claude Code to implement against specs, with a custom headless-Chrome test harness that checks logic and flows.

Core idea: shell and games are strictly separated. The shell is trusted; a game is an untrusted guest in a sandboxed iframe with an opaque origin. Everything a game may do is a message in a small, validated protocol.

The desktop shell

  • No framework. A tiny pub/sub bus (events.js) decouples modules: launch(id), state:change, repaired, win:focus... The launcher is the only module that knows how to open an app, so desktop, Start menu, Explorer and the Recycle Bin all call launch('id').
  • Window manager: a Window class with drag, 8-direction resize, maximize/restore animation, minimize to taskbar, z-order and focus, a modal-dialog subclass with parent dimming, "not responding" state. Resize handles and window jitter are part of the story: they are disabled until wm_core.exe is repaired.
  • Corruption as data: --corruption CSS variable = 1 - repaired/total, so wallpaper RGB-split, tear lines, taskbar glitches and icon-label scrambles scale smoothly and vanish at 100%. All motion respects prefers-reduced-motion.
  • Never hard-code the component count. Integrity is always repaired / GAME_IDS.length. This paid off when a game was removed late: integrity went from quarters to thirds without touching logic.
  • Edgy browser: an iframe per tab-less "browser", routes in registry.js (sys32://free-prizes...), history, favorites that appear once you have visited a game, and "Goggle" search with easter eggs. It never makes real network requests.
  • Explorer / Recycle Bin / Settings: data-driven from the registry. Settings is locked until admin_access.dll is repaired (a gameplay gate, not a permission).
  • Synthesized sound: every system sound is a few WebAudio oscillators, so the site ships no audio for the shell; sound is off by default.

Game protocol and the sandbox

Trust model

  • Iframes use sandbox="allow-scripts allow-forms allow-pointer-lock" and deliberately no allow-same-origin. The game's origin is opaque (null): it cannot read the shell's localStorage, cookies or DOM.
  • Because the origin is opaque, postMessage must use target '*'. Identity is therefore established by event.source === iframe.contentWindow, not by origin. The shell loops over its open frames and matches the source.
  • Games cannot be trusted for numbers: scores/times are validated (finite, non-negative, clamped), gameId must match the frame, easter-egg and achievement ids must start with the game's own prefix, unknown message types are ignored.
  • Games must be classic scripts (the core ones): module scripts need CORS, which an opaque origin cannot satisfy. The 3D games use ES modules plus an import map and load models/textures with fetch; this works because GitHub Pages sends Access-Control-Allow-Origin: *. A dedicated test (tests/cors-sandbox) proved this before I committed to the approach.

State, stores and resets

  • One in-memory object, three stores. system32.state (repairs, losses, skips, play time, tutorial progress, icon positions, README text, core bests), system32.meta (achievements, secrets, bonus games and bests, sound, accent, theme) and system32.save.<game> (world saves). Code everywhere reads state.x; save() splits it by a META_FIELDS list. This kept the change small: no call site had to learn about the split.
  • Why split at all? "Reset progress" must not destroy what the player earned (achievements, bonus unlocks, Strata world). With separate keys, reset is "wipe the state key"; Hard reset is "wipe every system32.* key" behind a typed DELETE.
  • Migration: versions 1 → 2 (bonus games) → 3 (meta). Merge sanitizes everything: unknown game ids (the removed game), removed egg ids, garbage types. If the meta key is missing but old state exists, meta is built from the old fields and achievements the old state proves are granted retroactively with one summary toast, after the boot sequence clears toasts.
  • localStorage hygiene: every read/write in try/catch; the app keeps running in memory if storage is blocked. World saves are separate keys with caps so a huge world can never corrupt the shell state.

The three core games

DOM-ination: pop-up survival

You close fake ad pop-ups before clutter reaches a cap; they spawn in waves with a boss ad and "bait" pop-ups. Technical points: real DOM elements as entities, fixed-timestep-ish loop with requestAnimationFrame, seeded RNG so playtests are reproducible, a ?debug=1 hook (window.__DOMINATION) with forceWin/forceLose/forceLosses that tests use. Achievement: win with clutter never above 12.

Inspect Element: the real DevTools is the puzzle

A bank login with three locks (find the password in an HTML comment, remove the disabled attribute, change a hidden role input). The player must use the browser's real DevTools. Design points: everything is delegated on document and elements are looked up by id on every call so deleting or recreating nodes can't crash it; a MutationObserver notices DevTools edits (ignoring writes the game makes itself via [data-ui]); the password is stored as reversed char codes so searching Sources only finds the comment; calling System32.won() from the console is allowed but gives "script kiddie" and zero stars (it is a hacking game, so cheating is a feature, tracked as an easter egg).

404: Window Manager

Drag file fragments into a Recovery window before their windows collapse; junk goes in the bin; three phases. Pointer-event drag with a drag layer, keyboard alternative (Space to pick up, Tab to choose a window), nested folders, seeded randomness, aria-live announcements.

Strata: the voxel engine

No Minecraft code or assets. Built from scratch with three.js only for rendering. Blocks use Kenney CC0 textures; mobs, hearts and many sounds are drawn/synthesized in code.

World representation

  • Chunks: 16×16×128 columns, one Uint8Array per chunk (a block is one byte, max 256 ids). Index (y<<8)|(z<<4)|x. World 1024×1024. A "partial block" (torch, chest, bed, plants) is a block id with a box or crossed-quad definition, not metadata, because the chunk format has no metadata byte; orientation variants are separate ids.
  • Generation: seeded value noise (own hash), biomes, caves via 3D noise, ores by depth, trees, bushes; spawn finder; flat mode for tests. Terrain is a pure function of (seed, chunk) so only edits need saving.
  • Dimensions: Overworld, Underlayer (512², no sky, basalt caves, lava, vaults) and the Kernel (128² arena over a void, regenerated on every entry, edits never saved). Switching dimension reloads the world with a different generator and edit map.

Worker architecture

  • Generation and meshing run in a Web Worker created from a Blob URL (so it works inside a sandboxed opaque-origin iframe); worker.js is self-contained (no imports), loadable as a classic worker, on the main thread (fallback, time-sliced) or in Node (so tests exercise the real code).
  • Typed arrays are transferred, not copied. The block table the worker needs is derived from the same blocks.js as the game (workerTable): one source of truth.
  • Meshing: only visible faces; per-vertex ambient occlusion (the 3-neighbour rule), quad diagonal flipped to avoid AO artefacts; three layers (opaque, cutout, water); animated tiles via a per-vertex frame count and a shader uniform.

Lighting

  • Two channels, sky light and block light (0..15), computed in the worker as a pure function of the 3×3 chunks around the chunk being meshed (48×128×48 region, flood fill with BFS). Because it's a pure function of blocks, a save/load gives identical lighting and nothing about light is saved.
  • Per-vertex smooth light (average of the front cell and corner neighbours). Day/night is a shader uniform, so the sky changing never triggers a remesh. A block change that can alter light remeshes the chunk and its 8 neighbours; other changes only touch the border neighbours.

Physics, entities, AI

  • Swept AABB collision per axis (x, z, then y) with a one-block step; fall damage from peak height; water/lava as fluids; sneaking never walks off edges.
  • A* pathfinding (600-node budget) with a weighted heuristic, wall-climbers (spiders) with a horizontal-only heuristic, stuck detection that replans, and avoidance of lava/deep water.
  • Mobs are code-built box models with a procedural texture atlas and synthesized voices. Animals are parked with their chunk and restored on load; hostiles spawn by light level (≤7), distance (24-64), a cap of 30, and lag out at sunrise.

Flowing water (late addition)

Water is a cell with strength: a source (8) and flowing blocks water_1..7. A tick every 0.25 s processes at most 400 queued cells: water with air below falls (and doesn't spread sideways); otherwise it feeds neighbouring air with strength−1, so it runs 7 blocks; flowing water with no feeder shrinks or drains; sources never dry up. Any setBlock queues the cell and neighbours, so digging beside a lake lets it in and a wall holds it back. Flowing water is just an edit in the save; chunk load re-queues its water cells. Mesher draws surface height by strength. Trade-off: not Minecraft-exact (no infinite sources, no levelling pools), chosen for simplicity and zero new save format.

Saves

  • Only edits are saved: per chunk, the list of (local index, block id) that differ from the generator, packed in binary, then deflate-raw compressed via CompressionStream, base64 (the shell stores strings). Header JSON holds seed, position, inventory, flags, vitals, drops, animals, chests.
  • Format STRATA1: v2 (migrates v1). Multiple worlds live in one shell string: STRATAW1: + JSON list of worlds, each carrying an unchanged STRATA1: save. Old single-world saves import as "World 1". Cap: 10 worlds, 4 MB total, 2.5 MB per world.

Strata gameplay systems

  • Survival: 20 HP, hunger with exhaustion, air, armor (4% per point, cap 80%), fall/lava/drowning damage, death piles (items drop where you died and last 10 minutes), difficulty levels, Creative mode with a searchable, sorted catalog of every item.
  • Progression chain: wood → stone → iron → cobalt ore (y 2-16) → cobalt pickaxe → Cracked Bedrock (found with the Tracer) → Rift → Underlayer → three Data Vaults (break spawner, lava parkour, shielded Vault Warden, shard) → Kernel Key → Kernel Gate → the Garbage Collector boss → ending, credits, System32.complete() once per world.
  • Boss (state machine): 300 HP, phases at 70%/35%. Marks (red blocks deleted after 3 s; step off), stomp then kneel exposing a core (double damage), charge with a wind-up, Pointers (flying cubes), four healing crystals, shrinking arena. A scripted bot beats it on Normal in ~80-120 s, which proves it is winnable and tunes difficulty numerically.
  • Objectives journal (J) + tutorial mode: 58 objectives in 6 acts, text as data in config.js, rules in objectives.js. Ticks come from events, counters and peak inventory counts (crafting a bow consumes the string, but "collect 3 string" stays done). Finishing a key objective implies earlier ones, so old saves and players who skip around still get a coherent list. State is a hex bitset in the world flags.

SpaceSaga

Three-lane endless runner on a small round planet: the vertex shader is patched so the track curves away with distance, GLB models from Kenney, obstacle patterns validated by a pure rules module (no impossible layouts), fixed 1/60 s step so pause is exact, synthesized music that densifies with distance. Reports RUN_OVER; distance milestones unlock achievements.

Testing strategy

  • Pure logic in Node: block table, worker generation and meshing, lighting, physics, survival rules, crafting, pathfinding, fluids, objectives, worlds list, sudoku. Possible because the worker and the logic modules have no DOM dependency.
  • Real-browser tests without dependencies: tests/lib/cdp.mjs is a tiny Chrome DevTools Protocol client (spawn headless Chrome and serve.py on free ports, scratch profile outside the repo). It sends real mouse and keyboard events, evaluates in the page and in iframes (evalInFrame), and screenshots on failure. No Playwright/Puppeteer, no node_modules.
  • Debug hooks (?debug=1): window.__STRATA etc. expose state and cheats so tests assert on behaviour rather than pixels.
  • Bot tests: a scripted bot plays the boss fight for several seeds and difficulties.
  • Honest limits: software WebGL means frame rate, game feel, sound quality and difficulty tuning are not verified headlessly; those need a human playthrough.

Bugs and what they taught

  • GitHub Pages broke everything: Jekyll skips folders starting with _, so games/_shared/sdk.js was a 404 and every game silently lost its link to the shell. Fix: .nojekyll. Lesson: test the deployed build, not just localhost.
  • Worker treated any truthy dimension as non-overworld, so Cracked Bedrock never generated; fixed with an explicit comparison and a regression test.
  • Rift return left the world size at 512 so the overworld read as bedrock; the world now remembers its main size.
  • Shell accepted timeMs: null as a 0 ms win because Number(null) === 0; validators are now strictly typed.
  • Ground friction every step slowed steering mobs to 60%; solved with a driven flag.
  • Boss killing blow marked the entity dead before the dying sequence; Mobs.damage returns "down" for bosses and phases are one-way.
  • Panel re-render swallowed clicks: a redraw between mouse-down and mouse-up replaced the button; fixed by re-rendering only when a content signature changes. Same class of bug as the Creative search box losing focus.
  • Fullscreen/INIT ordering and toasts cleared at boot: the retroactive-achievement toast was fired before the boot sequence wiped toasts; moved after desktop entry.
  • Test fixture mistakes (marks placed outside the platform, stale tab state, an await on a promise that resolves only when a dialog closes) taught me to distinguish product bugs from test bugs before changing the game.

Deployment

  • Static hosting on GitHub Pages from the repo root; all paths relative so it works under /system32/.
  • Needs .nojekyll (underscore folder). Pages also serves Access-Control-Allow-Origin: *, which the sandboxed 3D games rely on.
  • assets/source (original packs, ~187 MB) is git-ignored; only the built, trimmed assets are shipped.
  • serve.py is a local static server with sane MIME types for development.

Working with Claude Code

  • I wrote or directed specs (DESKTOP_SPEC, STRATA_PART2_SPEC, FINAL_SPEC...) with acceptance criteria and build order; Claude Code planned and implemented in phases, committing after green tests.
  • Guardrails I set: no push without being asked, no secrets or source assets committed, a size cap on staged files, no localStorage in games, mandatory stops for asset approval.
  • What I'd say honestly: AI did most keystrokes; my contribution was the product, the constraints, the architecture decisions (sandbox protocol, shell-owned state), verification, and judging trade-offs. I can explain every module's purpose and why it exists, and I know which parts are untested by hand (game feel, tuning).

Likely interview questions

How do you stop a game from cheating?

It can't write storage or call the shell's functions; it can only send messages. The shell identifies the sender by event.source, checks the game id and prefix, and validates every number and id. A forged win for another game, a null time, an unknown achievement id, or a too-early skip is ignored. The one deliberate exception is Inspect Element's console win, which is flagged as a "script kiddie" with zero stars.

Why is allow-same-origin missing and what does that cost?

With it, a sandboxed page that is same-origin could remove its own sandbox or read the shell's storage. Without it the origin is opaque: no storage of its own, module scripts fail without CORS, and postMessage must target '*'. I mitigate by verifying event.source and using classic scripts or CORS-enabled asset hosting.

How do you identify the sender if origins are opaque?

The shell keeps a list of its own iframes and compares e.source with each iframe.contentWindow. A different window cannot spoof that identity.

How does Strata avoid freezing the browser while generating terrain?

Generation and meshing run in a worker with transferable typed arrays, nearest chunks first, with a budget per frame for uploading meshes. If workers are unavailable there is a time-sliced main-thread fallback with the same code.

How does the lighting work and why isn't it saved?

It's a flood fill computed in the worker from the blocks of the 3×3 neighbouring chunks, for sky and block light. Since it's a pure function of the blocks, it is recomputed on load and always consistent. Day/night is a shader uniform, so time of day never remeshes.

How big is a save and how do you keep it small?

Only blocks that differ from the generator are stored, packed as 3 bytes each per chunk, deflate-compressed, base64 encoded. A typical world is well under 1.5 MB; caps are 2.5 MB per world and 4 MB for the list, with clear in-game messages when exceeded.

How did you implement multiple worlds without changing the shell protocol?

The shell still stores one string per game. Strata now stores a container STRATAW1: + JSON listing worlds, each holding an unchanged v2 save. A legacy save is detected by prefix and imported as "World 1". The container logic is pure and unit-tested.

How does pathfinding work and what are its limits?

Weighted A* on the voxel grid with a node budget (600), step/drop rules, lava and deep-water avoidance, climbing for spiders, and stuck detection with replanning. Limits: no hierarchical pathing, so long routes just fail gracefully and the mob wanders.

How do you test a 3D game headlessly?

Logic is in modules that run in Node (including the real worker). In Chrome I use software WebGL and debug hooks to assert state, plus screenshots for visual checks. I'm clear that frame rate and feel need a human.

Why not use a framework or TypeScript?

To keep deployment trivial and show I can structure a large app with modules, a bus and data-driven registries. For a team project I'd add TypeScript and a bundler; the module boundaries here would carry over unchanged.

What was the hardest bug?

Either the Pages 404 on an underscore folder (silent total failure that tests missed because they ran on a different server) or the world-size/dimension bugs when moving between overworld and Underlayer, where state that should have been per-dimension was global.

What would you do with more time?

Level-synchronised water and infinite sources, hierarchical pathfinding, service-worker caching for offline play, accessibility pass for the 3D games, automated visual regression, and a real playtest loop for difficulty tuning.

How did you keep scope under control?

Specs with explicit acceptance criteria, phase gates, and committing after green tests. The final spec removed a whole game; because progress was data-driven it was a small, safe change.

Is it accessible?

Shell: focus management, ARIA roles/labels on dialogs and panels, keyboard operation (Enter, Esc, arrows), prefers-reduced-motion and light/dark support. Games: keyboard alternatives in 404, subtitle option and sound toggle in Strata. Gaps: the 3D games aren't screen-reader friendly.

Security considerations?

Sandboxed untrusted frames, text inserted via textContent (never game strings as HTML), validated inputs, no network requests, no cookies, localStorage keys namespaced, typed-confirmation for destructive reset. The review gate in Claude Code also scans commits.

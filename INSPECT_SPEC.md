# INSPECT_SPEC.md — System32 Part 3: Inspect Element

> **File on desktop:** `bank_login.html` · **gameId:** `inspect` · **Repairs:** `admin_access.dll`
> **Route:** `sys32://bank-login` · **Folder:** `games/inspect-element/`
> **Target:** 1 day with Claude Code

A sketchy bank login page. You're locked out. The only way in is the **real browser DevTools**: read the source, edit the DOM, change values. Three locks stand between you and the dashboard, and each one teaches a single DevTools skill. Beat all three and you log in as **admin**, which is exactly what `admin_access.dll` needs.

**One mechanic:** inspect and edit the page with real DevTools. No timer, no lose condition. It's a puzzle; speed and hints decide the score.

---

## 1. Fit with the shell (read first)

Same rules as every game (see README "Building a game"):

- Classic scripts only, no `type="module"`.
- **No `localStorage`, no `document.cookie`.** On the sandbox's opaque origin, `document.cookie` throws a `SecurityError`. Every lock must work with plain DOM state.
- No `alert`/`confirm`/`window.open`. Errors are shown inline on the page.
- Talk to the shell only via `games/_shared/sdk.js`.

```html
<script src="../_shared/sdk.js" data-game="inspect"></script>
<link rel="stylesheet" href="style.css">
<script src="game.js"></script>
```

| When | SDK call |
|---|---|
| Page loaded | `System32.ready()` |
| Init | `System32.onInit(({ beaten, bestTimeMs, soundOn }) => …)` (shows "Best: 1:42" on the help card) |
| Lock solved | `System32.progress('locks', '2/3')` |
| Win (player clicks "Install") | `System32.won({ timeMs, score: stars })` |
| Minimized | `System32.onPause` / `onResume` stop and restart the elapsed-time clock only |

`GAME_LOST` is never sent: there's no way to lose.

### 1.1 How the player gets DevTools onto the game
The game lives in a sandboxed iframe inside the shell, so **F12 opens DevTools on the shell document**, not the game. The intended way in is **right-click inside the bank page → Inspect**, which opens Elements already pointed at the game's DOM. For the Console, the player must switch the JS context dropdown (top-left of the Console in Chrome, "iframe" picker in Firefox) to the bank page.

The game must teach this on its own (§5 Help card), because it's the #1 thing that will confuse players. The shell's existing Edgy `⋯ → Inspect (F12)` hint dialog should be updated to say: *"Right-click the page → Inspect. The real one."*

## 4. The three locks

### Lock 1 — The password (skill: reading the Elements panel / source)
In `index.html`, inside the login card, a set of HTML comments. One real, two red herrings:

```html
<!-- TODO: remove debug credentials before launch -->
<!-- password: ******** (lol nice try) -->
<!-- temp password for previous_user: hunter2 -->
<!-- note to self: stop leaving passwords in comments -->
```

- **Solved** when the password input's value equals `hunter2` (checked on `input` events, case-sensitive, trimmed).
- Comparison in `game.js` uses a light obfuscation (e.g. reversed char codes), so Ctrl+F in Sources for "hunter2" finds only the HTML comment. Reading the source still works; this just keeps the comment as the main path.
- Wrong password on submit: inline red text *"Incorrect password. 2 attempts remaining. (just kidding, infinite)"*.

### Lock 2 — The disabled button (skill: editing attributes)
```html
<button type="submit" id="login-btn" disabled title="Disabled for your security">Log in</button>
```
- **Solved** when the button is no longer disabled. Detect with a `MutationObserver` on the button's attributes **and** check `btn.disabled` on every pointer event over it, because setting `.disabled = false` from the Console changes the property but some browsers don't record an attribute mutation for it.
- Any method counts: deleting the attribute in Elements, `Edit as HTML`, or the Console.
- The form's `submit` handler always re-checks all three locks itself. Never trust the lock-row state alone.
- Implicit submission (pressing Enter in the password field) does nothing while the default button is disabled. That's native browser behaviour and is part of the puzzle.

### Lock 3 — The access level (skill: editing a value the page "trusts")
Inside the form:
```html
<input type="hidden" name="role" id="role" value="customer">
```
And a hint planted in the page as a hidden element (skill bonus: noticing `display:none` content in Elements/Styles):
```html
<div class="dev-note" style="display:none">
  security review: role check happens client-side. this is fine. 🔥
</div>
```
- After locks 1 and 2, submitting shows: *"Login successful. Access level: customer. Admin access required to restore admin_access.dll."*
- **Solved** when `#role` value is exactly `admin` at submit time (read `.value`, so both attribute edits and Console `.value =` work).
- Any other value → *"Unknown access level: '<value>'."* (escape the value with `textContent`, never `innerHTML`).

### Win
Submit with all three solved → 600 ms fake "Authenticating…" spinner → **dashboard**:
- "Welcome back, **admin**." Account balance `₹0.00` ("previous_user spent it on GPUs").
- A single item in "Downloads": **`admin_access.dll`** with an **Install** button → `System32.won(...)` → button becomes "Installed ✓".
- Stats: time, hints used, stars.

## 5. Help card (critical for players who've never opened DevTools)

The "?" button opens an inline card (not a pop-up window). It has:

1. **"How do I hack?"** (always visible, never costs a star): *"Right-click anywhere on this page and choose **Inspect**. That's the real DevTools, pointed at this page. Everything you need is in there."* Plus one line for the Console: *"Using the Console? Switch its context dropdown from 'top' to this page first."*
2. **Hints for the current lock**, revealed one tier at a time. Each tier revealed costs that lock's star (max one star lost per lock).

| Lock | Tier 1 | Tier 2 | Tier 3 |
|---|---|---|---|
| Password | "Developers leave notes. Not in the page, *in the code*." | "Look for grey `<!-- … -->` text near the login form in Elements." | "It's the one for previous_user." |
| Button | "Something is telling this button it can't be clicked." | "Select the button in Elements. Look at its attributes." | "Double-click `disabled` and delete it." |
| Access | "The bank checks who you are… on your computer." | "There's a hidden input in the form. Also a hidden note somewhere." | "Change the `role` input's value to `admin`." |

- **Nudge:** if no lock progresses for 60 s of unpaused time, the "?" button wiggles once. No auto-reveal.

**Stars (score):** start at 3, minus 1 for each lock where any tier 2+ hint was revealed (tier 1 is free). Minimum 0. Reported as `score`. `timeMs` is unpaused time from first interaction to clicking Install.

## 6. Easter eggs (report with `SHELL_EFFECT effect:'egg'`)

The DevTools mechanic means players will do weird things to the page. Reward the funny ones.

| id | Trigger | Effect |
|---|---|---|
| `inspect-script-kiddie` | `System32.won()` called from the Console before all locks are solved. `game.js` wraps `System32.won` after load and uses an internal flag for its own call. | The win still goes through (it's a hacking game), but the dashboard greets *"Welcome back, script kiddie."* and stars = 0. |
| `inspect-deleted-bank` | A `MutationObserver` on `<body>` sees `#login-card` removed | Inject a small message into the body: *"You deleted the bank. Honestly? Fair. Press ⟳ to restore it."* |
| `inspect-rich` | On the dashboard, the balance text is edited to anything else (observer on the balance node's text) | A line appears under it: *"The money is fake too."* |
| `inspect-wrong-door` | The password field's `type` is changed from `password` to `text` (a real DevTools trick) | Tiny text under the field: *"Ah, a classic."* |

## 7. Implementation notes

- **State:** `{ startedAt, elapsedMs, paused, locks: {password, button, role}, hintsRevealed: {…}, won }`. Elapsed time is driven by a `requestAnimationFrame` clock that skips paused time. Start counting on first pointer or key event in the page.
- **Lock detection:** re-evaluate all locks on `input`, on the mutation observers, and on `pointerover`/`focus` of the button. Updating the lock row is idempotent; the solved-sound plays only on a false → true transition.
- **Robust to DOM surgery:** players will delete and recreate nodes. Look up elements by id each time (`document.getElementById`) instead of caching references, and fail gracefully if missing.
- **Submit handler:** `preventDefault()`, then check in order: password → button (the button's own `disabled` state) → role. Show only the first failing message.
- **Never use `innerHTML` with anything the player can edit.** Use `textContent`.
- **Don't try to detect whether DevTools is open.** It's unreliable and not needed.
- **Sound** (only if `soundOn`): WebAudio click per lock, low buzz on a wrong submit, three-note rise on win.
- **Reduced motion:** no spinner rotation (show static "Authenticating…"), no Help-button wiggle.

## 8. Testing hooks

- `?debug=1` exposes `window.__INSPECT = { state(), solve('password'|'button'|'role'), reset() }`.
- A headless test should solve each lock the way a player would: set `#password` value and dispatch `input`, `removeAttribute('disabled')`, set `#role` value, submit the form, click Install, and assert `GAME_WON` arrives once in the shell.
- Also test: wrong password message; locks 1+2 with role still `customer` gives the access-level message; Console-path `.disabled = false` solves lock 2; `System32.won()` early triggers the script-kiddie egg.

## 9. Acceptance criteria

- [ ] Page loads inside Edgy; `GAME_READY` is sent; the three puzzle elements are present as static HTML.
- [ ] Right-click → Inspect in Chrome and Firefox lands in the game's DOM (manual check).
- [ ] Each lock is solvable through Elements editing **and** through the Console (with the iframe context selected).
- [ ] Lock row updates live; progress chip shows `locks n/3`.
- [ ] Submit shows the first failing lock's message; all three solved → dashboard → Install sends `GAME_WON` once and the shell repairs `admin_access.dll` (Settings unlocks).
- [ ] Help card: "How do I hack?" is free; tiered hints reveal one at a time; stars computed as in §5.
- [ ] Pause stops the clock exactly; no lose condition, no `GAME_LOST`.
- [ ] All four easter eggs fire and are added to the shell's egg registry (secrets total goes from 18 to 22).
- [ ] Deleting or recreating nodes never throws an uncaught error.
- [ ] No cookies, `localStorage`, `innerHTML` with player-editable data, modals or module scripts. No console errors.
- [ ] Shell's Edgy `⋯ → Inspect` dialog text updated per §1.1.
- [ ] Playtest with someone who has **never** opened DevTools: they finish using hints in under 10 minutes.
